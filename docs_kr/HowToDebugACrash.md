# 충돌 디버깅을 위해 Addr2Line 도구를 사용하는 방법
**addr2line**는 Linux에서 Toolchain와 함께 제공되는 도구입니다.
주어진 주소를 파일 이름과 줄 번호로 변환합니다.  
개발자는 **addr2line**를 통해 TizenRT ELF/AXF 출력 파일을 디버그할 수 있습니다.
충돌을 디버깅하는 동안 특히 유용하며 오류를 찾는 데 사용할 수 있습니다. 
충돌이 발생한 정확한 줄 번호 및 함수 호출 스택
이로 인해 충돌이 발생했습니다.

## 전제 조건
1. addr2line를 사용하려면 아래 구성을 활성화하세요.  

menuconfig에서 **CONFIG_DEBUG_SYMBOLS**를 활성화합니다.

```
menuconfig -> Debug Options -> Generate Debug Symbols
```

2. 시스템 경로에 툴체인 추가
툴체인이
PATH 환경 변수를 사용하는 시스템 경로입니다.
예를 들어, ARM 도구 체인이 다음 위치에 있는 경우:

```
/home/tools/gcc-arm-none-eabi-9-2019-q4-major
```
그런 다음 PATH 변수에는 다음과 같이 툴체인 bin 폴더가 포함되어야 합니다.

```
/home/tools/gcc-arm-none-eabi-9-2019-q4-major/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

3. 스택 덤프 활성화
시스템에 충돌이 발생하면 충돌이 발생한 정확한 위치를 알아내는 것이 유용하며,
충돌을 일으킨 함수 호출 스택. 이를 찾으려면 해당하는 내용을 인쇄해야 합니다.
충돌이 발생할 때 주소 값. 이는 다음 구성을 활성화하여 수행할 수 있습니다.

CONFIG_ARCH_STACKDUMP
```
menuconfig -> Chip selection -> Dump stack on assertions
```

<a id="how-to-use-addr2line"></a>
## addr2line 사용법
빌드 후 Linux 셸에서 **addr2line**를 사용합니다.  
Linux 매뉴얼 페이지를 참조하십시오.  
(https://man7.org/linux/man-pages/man1/addr2line.1.html)  
간단한 명령은 아래와 같습니다.  
```
$ addr2line -e [filepath] -a [address]
```

그러나 툴체인 경로가 위에서 언급한 대로 구성되지 않았거나 시스템에 여러 툴체인이 설치되어 있는 경우,
그런 다음 사용할 addr2line의 올바른 버전을 지정해야 할 수도 있습니다. 다음과 같이 수행할 수 있습니다.

아래 명령은 ARM 툴체인이 사용되도록 지정합니다.
이 작업을 수행하려면 PATH에서 ARM 도구 체인을 구성해야 합니다.
```
$ arm-none-eabi-addr2line -e [filepath] -a [address]
```

그러나 툴체인 경로가 구성되지 않았거나 여러 버전의 툴체인이 있는 경우 전체 경로를 지정할 수 있습니다.
에는 다음과 같이 addr2line 도구가 필요합니다.
```
$ /home/tools/gcc-arm-none-eabi-9-2019-q4-major/bin/arm-none-eabi-addr2line -e [filepath] -a [address]
```

### 이진 분리에 사용하는 방법
바이너리 분리가 활성화되면 사용자 바이너리의 텍스트 섹션 주소가 0x0부터 시작하여 재배치됩니다.  
재배치 후 실제 주소가 할당되고 해당 주소를 디버깅에 사용할 수 있습니다.  
이를 위해서는 아래와 같은 몇 가지 단계가 필요합니다.  

1. 다음 구성을 활성화합니다.

	CONFIG_SAVE_BIN_SECTION_ADDR  
	```
	menuconfig -> Binary Loader -> Save binary section address
	```

	CONFIG_DEBUG_BINFMT_INFO
	```
	menuconfig -> Debug Options -> Enable Debug Features -> Binary Loader Debug Features -> Binary Loader Informational Output
	```

2. 인쇄된 로그에서 사용자 바이너리의 텍스트 주소를 확인하세요.  

3. 2번을 기준으로 주소를 계산합니다.  
예를 들어 사용자 바이너리 텍스트 주소가 0x1000000이고 기호 주소 ix 0x1200000라고 가정합니다.  
그런 다음 0x1200000에서 0x1000000를 빼고 이 주소를 -a 옵션의 매개변수에 전달합니다.
	```
	$ addr2line -e [filepath] -a 0x200000
	```

## addr2line로 충돌을 디버깅하는 방법
시스템에 충돌이 발생하고 위 구성이 활성화된 경우 시스템은 현재의 스택 덤프를 인쇄합니다. 충돌이 발생한
실행 작업과 충돌 당시 CPU 레지스터의 내용을 표시하는 레지스터 덤프도 있습니다.
그런 다음 위에서 설명한 대로 addr2line 명령을 사용하여 인쇄된 주소 값을 소스 파일 행 번호로 변환하고
다음과 같은 디버그 정보를 얻을 수 있습니다.

1. 충돌이 발생한 위치
이는 레지스터 덤프에서 찾을 수 있습니다. 레지스터 덤프에는 R0~R15 레지스터의 값이 포함되어 있습니다. R15 레지스터는 다음을 제공합니다.
PC(프로그램 카운터) 값입니다. 이 주소는 addr2line 명령과 함께 사용되어 소스 코드에서 정확한 줄 번호를 찾을 수 있습니다. 충돌을 일으킨
. 충돌 중

2. Callstack
콜스택은 스택 덤프에 출력된 주소 값에서 찾을 수 있습니다. 그러나 스택 덤프에는 유효한 주소와
기타 HEX 값. 콜스택 함수 주소가 저장되는 스택 덤프의 정확한 위치를 확인할 방법이 없습니다.
따라서 스택 덤프에서 예상되는 주소 값을 수동으로 찾아야 합니다. 주소를 알면 가능합니다
텍스트 섹션이 메모리에 로드됩니다. 이 정보는 일반적으로 특정 프로젝트 또는 앱의 링커 스크립트에 있습니다.
특정 링커 스크립트.

예를 들어 링커 스크립트에서 텍스트 섹션이 주소 0x80000000에서 0x84000000 사이에 로드되어 있다고 가정합니다.
이제 스택 덤프에서 이 주소 범위의 값을 검색합니다. 스택 덤프의 첫 번째 줄은 가장 최근 함수를 나타냅니다. 충돌 당시
이며 마지막 줄은 호출 스택에서 가장 오래된 함수를 나타냅니다. 위 범위의 각 유효한 주소에 대해
인 경우 addr2line 도구를 사용하여 소스 코드 줄 번호를 찾습니다. 따라서 충돌 시 호출 스택을 재구성할 수 있습니다.

<a id="Understanding-debug-messages-during-a-fault"></a>
## 오류 중 디버그 메시지 이해
메모리 오류, 사용 오류, 하드 오류 등 오류 중 하나로 인해 충돌이 발생할 수 있습니다. 오류가 발생하면 하드웨어는 해당 오류 상태 레지스터에 오류 원인을 인코딩합니다. 오류 처리기는 이 레지스터의 내용을 16진수 형식으로 인쇄하고 오류 원인에 대한 간략한 설명도 제공합니다. 다음 섹션에서는 각 오류 시나리오를 이해하고 디버그하기 위한 추가 정보와 팁을 제공합니다. 여기에서는 각각 memfault, Busfault, Usage Fault 및 Hard Fault에 대해 MMFSR, BFSR, UFSR 및 HFSR 레지스터에 인코딩된 다양한 오류 시나리오에 대해 설명합니다. 이러한 레지스터와 해당 비트 필드에 대한 설명을 찾으려면 해당 아키텍처의 ARM 아키텍처 참조 매뉴얼을 참조하세요.

Armv7-m : https://developer.arm.com/documentation/ddi0403/eb/

Armv8-m : https://developer.arm.com/documentation/ddi0553/latest

### MemManage 오류 상태 레지스터(MMFSR)

1. ```MMARVALID```

디버그 메시지: 주소(MMFAR)에서 액세스 위반이 발생했습니다: 0xAddress

이 메시지는 memfault를 일으킨 주소를 사용할 수 있음을 나타냅니다. 인쇄된 주소 값을 확인하세요. 주소가 0이면 널 포인터 액세스로 인해 발생한 것일 수 있습니다. 주소 값이 0이 아닌 경우 다음 이유 중 하나로 인해 오류가 발생할 수 있습니다. 
- 주소가 구성된 MPU 지역 외부에 있습니다.
- MPU 지역 구성이 액세스 유형과 일치하지 않습니다. 예를 들어 읽기 전용 영역에 쓰려고 하면


디버그 메시지: 액세스 위반 주소를 확인할 수 없습니다.

이 메시지는 하드웨어가 오류를 일으킨 주소를 찾을 수 없음을 나타냅니다. 이는 일반적으로 명령 액세스 위반의 경우에 발생합니다. 그러나 디버그 로그에는 충돌 당시의 PC 및 LR 레지스터 값이 표시됩니다. PC 레지스터에 잘못된 주소가 포함되어 있습니다. 개발자는 충돌의 근본 원인을 찾으려면 추가로 디버깅해야 합니다. 다음 지침을 사용할 수 있습니다.
- PC 값이 유효한 주소인 경우 유효한 MPU 영역(실행 권한 포함)에 속하는지 확인합니다.
- PC 값이 완전히 잘못된 것 같으면 코드에서 모든 위치를 찾아야 하며 이로 인해 PC 값이 비순차적으로 변경될 수 있습니다. 잘못된 함수 포인터 또는 컨텍스트 전환이나 irq 처리 중에 PC에 잘못된 값이 채워졌기 때문일 수 있습니다.
- 개발자는 LR 값을 사용하여 이전 기능을 찾은 다음 수동으로 코드를 살펴보며 PC 손상의 가능한 원인을 찾을 수 있습니다.


위의 두 경우 모두 개발자는 addr2line 도구를 PC 및 LR 값과 함께 사용하여 코드에서 오류가 발생한 줄 번호를 찾을 수 있습니다. 다음 사항에 유의하세요.
- LR 값은 함수 호출에서 반환된 후 실행될 다음 명령을 가리킵니다. 따라서 LR은 오류가 발생한 기능 뒤의 줄 번호를 가리킵니다.
- 함수가 "인라인"으로 선언되었거나 일부 컴파일러 최적화로 인해 함수가 인라인된 경우 LR 및 PC에 정확한 줄 번호가 포함되지 않을 수 있습니다.


2. ```DACCVIOL```

디버그 메시지: 데이터 액세스 위반이 발생했습니다.

PC 값과 디버그 메시지에 인쇄된 주소를 사용하여 위의 (1) 항목에서 언급한 것처럼 어떤 변수가 잘못된 데이터 액세스를 일으키는지 알아보세요.


3. ```IACCVIOL```

디버그 메시지: XN(Execute Never) 영역에서 명령어를 가져오는 동안 명령어 액세스 위반이 발생했습니다.

실행 권한 없이 MPU 영역에서 실행됩니다. PC의 라인 번호를 확인하여 해당 MPU 지역에 적절한 권한이 있는지 확인하세요. 


4. ```MSTKERR``` 및 ```MUNSTKERR```

디버그 메시지:
예외 항목 중 레지스터를 스태킹하는 동안 오류가 발생했습니다.
또는
예외 반환 중 레지스터를 스택 해제하는 동안 오류가 발생했습니다.

이 두 경우 모두 스택 처리 중에 데이터 액세스 위반이 발생했습니다. 따라서 스택 포인터 값을 확인하여 스택 내에 있는지 확인하십시오. 또한 스택 처리는 함수 호출/반환의 경우와 예외 처리의 경우에 발생합니다. 따라서 개발자는 예외 처리 코드의 온전성을 확인해야 할 수도 있습니다.


5. ```MLSPERR```

디버그 메시지: 부동 소수점 단위 레지스터의 지연 상태 보존 중에 오류가 발생했습니다.

이 비트는 또한 예외 처리 중 레지스터 스태킹 중 오류를 나타냅니다.


### 버스 오류 상태 레지스터(BFSR)
버스 오류는 위에서 언급한 메모리 관리 오류와 매우 유사합니다. 유효하지 않은 메모리 주소에서 데이터나 명령에 액세스하면 버스 오류가 발생할 수 있습니다. MPU가 활성화되면 대부분의 잘못된 액세스로 인해 해당 memfault가 발생합니다. 그러나 MPU가 비활성화되면 잘못된 모든 메모리 액세스로 인해 버스 오류가 발생합니다. 버스 오류는 데이터 또는 명령어에 액세스하는 동안 오류가 발생했는지 여부에 따라 데이터 중단 또는 프리페치 중단이 될 수 있습니다. 이 레지스터의 BFARVALID, STKERR, UNSTKERR, LSPERR 필드는 memfault 시나리오의 해당 비트와 유사합니다. IBUSERR 비트는 명령어 액세스 오류를 나타냅니다. 반면 PRECISERR 및 IMPRECISERR 비트는 데이터 액세스 위반을 나타냅니다. PRECISERR은 memfault 레지스터의 DACCVIOL과 유사합니다.

유일한 차이점은 IMPRECISERR 비트에 있습니다. 부정확한 데이터 액세스 위반이 발생한 경우 이 비트가 설정됩니다. 이는 현재 PC 값이 데이터 액세스 위반을 일으킨 명령을 가리키지 않음을 의미합니다. 위반은 일부 이전 명령어로 인해 발생했지만 메모리 액세스가 항상 동기화되지 않기 때문에 지연되었습니다. 이러한 유형의 오류를 디버깅하기 위해 개발자는 현재 PC 값에서 시작하여 이전 몇 줄의 코드를 확인할 수 있습니다. 개발자는 또한 objdump 도구를 사용하여 현재 PC 값에서 코드 분해를 인쇄한 다음 값을 메모리에 로드하거나 저장하는 각 어셈블리 명령을 확인할 수 있습니다.


### UFSR(사용 오류 상태 레지스터)

1. ```DIVBYZERO```

0으로 나누기 오류를 나타냅니다.

2. ```UNALIGNED```

정렬되지 않은 메모리 액세스를 나타냅니다.

3. ```UNDEFINSTR```

정의되지 않은 명령 실행을 나타냅니다.

4. ```STKOF```

스택 오버플로를 나타냅니다.

5. ```NOCP```

보조 프로세서가 비활성화되었음을 나타냅니다.

6. ```INVPC```

이 비트는 예외 반환 중에 무결성 검사가 실패하는 경우 설정됩니다. 이는 다음 이유 중 하나로 인해 발생할 수 있습니다.
- IPSR 레지스터에 보관된 예외 번호가 현재 예외(SHCSR 레지스터에 설정된 해당 비트)와 일치하지 않는 경우.
- EXC_RETURN의 비트[1]가 (1)로 설정된 경우. EXC_RETURN는 예외 반환 당시 R14의 값입니다.
- 스레드 모드로 돌아가고 IPSR이 (0)으로 복원되지 않는 경우.
- 핸들러 모드로 돌아가고 IPSR이 0이 아닌 값으로 복원되지 않는 경우.
개발자는 위의 조건 중 하나가 발생할 수 있는 코드를 확인해야 합니다.

7. ```INVSTATE```

PC 레지스터의 비트[0]는 항상 (1)로 설정되어야 합니다. 이 조건이 충족되지 않으면 INVSTATE 예외가 생성됩니다. 이 결함을 디버깅하려면 개발자는 잘못된 값으로 PC를 로드할 수 있는 명령을 확인해야 합니다.


### 하드 오류 상태 레지스터(HFSR)
하드 오류의 가장 일반적인 원인은 다른 오류의 확대입니다. 이는 오류 조건이 발생했지만 해당 오류가 하드웨어에 의해 구현되지 않거나 활성화되지 않은 경우에 발생합니다. 예를 들어, 메모리 액세스 위반이 발생하고 memfault 및 버스폴트가 활성화되지 않은 경우 하드 오류로 에스컬레이션됩니다. 이러한 에스컬레이션으로 인해 하드 오류가 발생한 경우 HFSR에서 FORCED 비트가 (1)로 설정됩니다. 하드 오류 처리기는 위에서 언급한 모든 오류 레지스터의 값을 인쇄합니다. 개발자는 이러한 레지스터 값에서 어떤 오류가 발생했는지 확인한 다음 위에서 언급한 해당 오류 시나리오에 대한 지침에 따라 디버깅을 수행할 수 있습니다.
